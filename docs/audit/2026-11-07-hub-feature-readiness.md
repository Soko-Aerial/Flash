## Already built

Invite enrolment, device certificates and renewal, device revocation on the server, scoped admin APIs, directory and hidden departments, groups and join requests, relay and offline mailbox, sealed Hub file transfers, announcements and in-app unread counts, audit and metrics, and the enrolled Hub workspace are present. The Android and desktop apps also have offline organisation trust and signed group roster exchange. Phone co-signing exists for the configured high-risk admin actions when an approver is bound. Its scope differs from the older backlog's proposed phone signer for all step-up actions.

## Partial workflows and policy decisions

| **Group access after removal** | The relay checks membership when queuing. Its mailbox drain replays queued group payloads without a current-membership check. A removed member with valid Hub enrolment can therefore receive messages that were queued before removal. Group file downloads already check live membership. Decide the chat policy before rollout. If removal is intended to cut off unread Hub data, enforce it at delivery and retire skipped rows with a truthful sender outcome. Also verify that sends after removal never reach the former member. ## Operational acceptance

1. **Give operators actionable health.** Prometheus-format metrics, mailbox quarantine telemetry and file audit events exist. Alert on quarantine growth, oldest queued message, disk pressure and certificate/delegation expiry. Put recovery instructions next to those alerts. Run a restore and a delegation rotation/revocation drill with existing clients before the first pilot.
2. **Run a real pilot matrix.** Use an isolated Hub, an organisation admin, a head of two departments, two Android phones and a Windows client. Exercise onboarding, hidden departments, scoped announcements, offline removal, cross-network chat/files, process restart, delivery and operator recovery. Reuse `DEPH-*`, `PRIV-*`, `ORGT-*`, `HUBR-*`, `ANN-*`, `HUBWORK-*` and `CONSOLE-D02..07`. Run a soak at the intended fleet size before publishing capacity numbers. `PERF-H03` is still owed.
3. **Keep deployment-specific expansion separate.** Notification wake-up needs a delivery target and platform validation if users must receive alerts while the app is unavailable. High availability and identity-provider provisioning depend on the organisation's availability and account-management needs. The roadmap explicitly parks multi-org, multiple devices per member and announcement extras.

## Verification and limits

Console Node tests passed 83/83. The locked Gradle server gate passed 23/23 across department scope, announcement admin routes, phone approval API, lifecycle and restart contracts.

Three temporary JVM probes reproduced current behaviour. The probes used the existing Ktor route and real-socket E2E fixtures through an external Gradle test source directory. They were written to assert the observed behaviour. They were not added as product regression tests.

| Probe | Observed |
|---|---|
| `multiDepartmentHeadGetsEmptyListEvenWithExplicitInScopeFilter` | An org admin saw two department posts. A head scoped to both received HTTP 200 with zero items on both the unfiltered list and `?departmentId=dept-a`. ERROR-996. |
| `missingDataKeyIsSilentlyRecreatedWhileAnExistingMailboxRowIsSealed` | Stopped a disposable Hub with a sealed queued row, deleted its key, then restarted. Startup succeeded, generated a different key, and retained the old row. ERROR-997. |
| `hubReplaysGroupMessageToDeviceRemovedBeforeReconnect` | Queued a group message while the recipient was offline, removed the recipient from that group, then reconnected the enrolled recipient. The transport received the payload with `replay=true`. The probe establishes server delivery, independent of what the client UI displays. |
