## 1. Behaviour in one page

- An **announcement** is a one-way message with a title and a plain-text body, scoped to the **whole company** or to **one department**.
- **Who can post:** org admin → company-wide or any department; department head → only their own department(s). Employees cannot post. Posting from the **app** uses the device certificate (role `admin` or `dept_admin` + department); posting from the **console** uses the console login (`ORG_ADMIN`, or `DEPT_HEAD` with its department scope, Plan A1).
- **Who can read:** company-wide → every enrolled member; department-scoped → members and admins/heads of that department only (even if the department is not hidden: announcements are never visible to outsiders).
- Stored on the hub **as plain text** (owner decision). The hub operator, org admins and (for their department) heads can read everything; the app says so (exact text §9).
- **Search**: server-side (console and app, online) and local over the device's cached announcements (offline).
- **Console preview**: when composing, the console shows the announcement as the phone will render it.
- Live delivery: a small push to connected devices; devices catch up with a changes feed when they reconnect. No FCM (the owner rejected it earlier; background delivery follows the known platform limits, see §6.4).
- Pinned announcements (max 3 company-wide, max 3 per department); optional expiry; edit and delete by authorised people.

## 3. Server

### 3.1 Schema (component "announcements", new migration; VERIFY `Migrations.kt`)
```
announcement(
  id TEXT PRIMARY KEY,                -- UUIDv4 generated by the server
  scope TEXT NOT NULL,                -- 'org' | 'department'
  department_id TEXT,                 -- NULL for org; required for department
  title TEXT NOT NULL,                -- 1..120 chars after sanitising
  body TEXT NOT NULL,                 -- 1..4000 chars after sanitising
  author_kind TEXT NOT NULL,          -- 'device' | 'console'
  author_ref TEXT NOT NULL,           -- device id or console username
  author_name TEXT NOT NULL,          -- snapshot of the display name at posting
  author_role TEXT NOT NULL,          -- 'admin' | 'dept_admin'
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  edited INTEGER NOT NULL DEFAULT 0,
  pinned INTEGER NOT NULL DEFAULT 0, pinned_at INTEGER,
  expires_at INTEGER,                 -- NULL = never
  deleted_at INTEGER,                 -- tombstone (kept for sync, purged after 90 days)
  seq INTEGER NOT NULL,               -- global monotonic change counter (every create/edit/delete/pin gets a new seq)
  kind TEXT NOT NULL DEFAULT 'text',  -- reserved: later 'ack_required' etc.
  flags INTEGER NOT NULL DEFAULT 0    -- reserved
)
INDEX announcement_scope_seq(scope, department_id, seq)
INDEX announcement_created(created_at DESC)
announcement_state(key TEXT PRIMARY KEY, value TEXT)   -- 'seq' counter, 'epoch' random id (new epoch if the database is restored: seq lower than a persisted high-water mark file, as in Plan B §5.4)
announcement_request(client_request_id TEXT PRIMARY KEY, announcement_id TEXT, created_at INTEGER)   -- idempotency, purged after 10 min
```
Full-text search: SQLite **FTS5** virtual table `announcement_fts(title, body, content='announcement', content_rowid=rowid)` maintained in the same transaction as every write. **VERIFY** the bundled SQLite JDBC driver has FTS5 (write a tiny startup self-test); if not, fall back to `LIKE` with escaping and a `LIMIT`, and record the fallback in the Implementation log.
The visibility filter (scope/department) is applied **inside the SQL** that feeds ranking, never after.

### 3.2 Sanitising (one function `AnnouncementText.clean(title, body)` used by every route)
Reject (400) if empty after trimming. Normalise to NFC. Remove ASCII control characters except `\n` and `\t`. Remove Unicode bidirectional **override/embedding/isolate controls** (U+202A–U+202E, U+2066–U+2069) to prevent spoofed text; remove zero-width characters (U+200B–U+200D, U+2060, U+FEFF) from the **title** (kept in body only inside emoji sequences — implement as: strip them everywhere except U+200D between two emoji code points; if that is too fiddly, strip U+200B/U+2060/U+FEFF only and leave U+200D). Collapse more than 3 consecutive newlines to 3. Length limits are counted in **Unicode code points**. The body is **plain text**: the server never interprets HTML/markdown; the client renders it as text. Golden tests with hostile inputs (RTL override, `<script>`, long emoji sequences, 4,001 code points, only whitespace, NUL bytes).

### 3.3 REST for devices (bearer auth, same as other `/api/v1` routes; add to `docs/protocol-routes.txt` and `docs/protocol.md` section "Announcements v1")
| Route | Who | Notes |
|---|---|---|
| `GET /api/v1/announcements?since=<seq>&limit=<n>` | any member | **Changes feed**: all visible announcements with `seq > since`, including tombstones (`deleted: true`, no title/body) and pins; response `{epoch, seq, fullResync, items[], nextCursor?}`; default limit 100, max 200; `since=0` → newest-first initial page logic described in §3.4 |
| `GET /api/v1/announcements?q=&scope=&departmentId=&before=<createdAt>&limit=` | any member | **Search/browse older** (online): `q` ≤ 64 chars; results ranked by recency (FTS rank secondary); visibility filter in SQL |
| `GET /api/v1/announcements/{id}` | any member allowed to see it | 404 otherwise (no oracle) |
| `POST /api/v1/announcements` | cert role `admin`, or `dept_admin` for the **cert's own department** | body `{clientRequestId, scope, departmentId?, title, body, pinned?, expiresAtMs?}`; idempotent on `clientRequestId` |
| `PUT /api/v1/announcements/{id}` | author, org admin, or a head of that department (rules §3.5) | body `{expectedSeq, title, body, pinned?, expiresAtMs?}`; `expectedSeq` mismatch → 409 with the current item |
| `DELETE /api/v1/announcements/{id}` | same as edit | soft delete (tombstone) |
| `POST /api/v1/announcements/{id}/pin`, `…/unpin` | org admin; head for own department | max pinned: 3 company-wide, 3 per department (409 with sentence) |

All write routes: body size cap 16 KB; rate limits per device: 5 posts/min, 30/day (429 + `Retry-After`); audit rows (`announcement.create|edit|delete|pin|unpin`) with id, scope, department, author, **body length only (never the body or title)**.
Authorisation uses the **certificate role and department the hub verified at the request**, never fields from the body (`departmentId` in the body must equal an allowed department or the request is 403).

### 3.4 Initial sync shape
`since=0` returns the **newest 200** visible, non-expired, non-deleted announcements (pinned first), `fullResync=true`, plus `seq` (the highest). Older ones are available through search/browse (`before=`). Deltas after that use `since=seq`. The client keeps at most 500 announcements / 12 months (pinned and unread are kept first).

### 3.5 Who may edit/delete/pin (decided here; accepted by the owner 2026-10-14)
| Actor | Create | Edit/Delete | Pin |
|---|---|---|---|
| Org admin (app cert or console) | org or any department | any | any |
| Department head | own department only | announcements **in their department** authored by a head (any head of that department, including themselves); **not** admin-authored ones | own department |
| Employee | no | no | no |
Author later demoted/revoked: their announcements stay; an org admin can edit/delete them; heads of the department too (if head-authored).

### 3.6 Admin console routes (`/admin/api/v1/announcements*`, scope via Plan A1's `ConsoleScope`)
`GET /admin/api/v1/announcements?q=&scope=&departmentId=&author=&state=active|expired|deleted&pinned=&limit=&cursor=`, `POST` (create), `PUT /{id}`, `DELETE /{id}`, `POST /{id}/pin|unpin`, `POST /admin/api/v1/announcements/preview` (returns the sanitised title/body, character counts, detected links, and which audience will see it with an estimated recipient count; **no state change**). Heads: only departments in scope; org-wide and other departments → 404/403 as in Plan A1; step-up not required.
Console author fields come from the login (`display_name`, role). If a head login has `linked_device_id`, show the same author name as the app would.

### 3.7 Live push (relay)
New relay frame **`AnnouncementEvent`** (server → client only): `{type:"ann", id, seq, scope, departmentId?, change:"new"|"edit"|"delete"|"pin", epoch}`. **No title/body in the frame.**
- Gate by capability: the client declares `ann1` in `Hello` (VERIFY the field; add `features: List<String>` to `Hello` with `ignoreUnknownKeys`), the server stores it on the session and only then sends the frame. Test: an old client without the capability never receives it; an old client that *does* receive an unknown frame (defensive test) does not crash (VERIFY client behaviour; fix only if tiny, otherwise rely on capability gating).
- Recipients: org scope → all live sessions; department scope → live sessions of members of that department (+ admins). Use `RelayConnectionPool` (read the API). Best-effort; losses are fine: the changes feed is the truth.
- Frame spec in `docs/protocol.md` with a golden JSON vector in `core/hub-protocol` tests; contract tests (`RelayDeliveryContractTest` style).
- Server-side fan-out must not block the posting request (bounded queue, drop on slow consumers with a counter metric).

### 3.8 Retention and settings
Server setting `announcementRetentionDays` (0 = keep for ever, max 3650) edited in the console Settings view (step-up `SETTINGS_CHANGE`); a daily purge job hard-deletes expired/old announcements and tombstones older than 90 days, updating FTS in the same transaction, and writing one audit row with counts. Limits (title 120, body 4000) are server constants exposed in `GET /api/v1/hub` (`announcementLimits`) so the app does not hard-code them.

## 6. Security and robustness expectations (requirements)
1. Authorisation from verified cert/console session only; matrix test (actor × route × scope) like Plan A1.
2. Visibility filter inside SQL (also for FTS and counts). Test that an outsider's search for a unique word of a department announcement returns 0 rows and no count leak.
3. Idempotent posting (`clientRequestId`); duplicate request returns the same item with 200.
4. Optimistic concurrency on edit (`expectedSeq`).
5. Size caps at the HTTP layer (16 KB) and in `clean`; code-point counting.
6. Rate limits and metrics; slow-consumer protection on push.
7. No announcement text in logs, audit rows, metrics labels, crash reports, or notifications beyond the title on the device.
8. Epoch/seq regression after restore → clients resync fully, not corrupt (test with a manually lowered seq).
9. Clock: all ordering from server `seq`/timestamps; device clock only for display.
10. Old apps ignore the new frame and never see the routes; new app against a hub without announcements hides the News section and shows `org_ann_unsupported`.
11. Revoked/unenrolled device: stored announcements are deleted with the rest of the organisation data; push stops.
12. Plain text is a decision: do **not** add markdown/HTML rendering without a new ADR (injection and phishing surface).

## 7. Situations the plan does not spell out (expectations)
- Posting while offline: **not queued**; the composer keeps the draft (persist in settings, per device) and shows `org_ann_offline`; never silently posts later.
- Double tap on "Post": button disables; idempotency key protects.
- Edit while someone else deleted it: 404 → "This announcement was removed."
- Department deleted or announcement's department hidden later: announcements stay visible to that department's members; if the department is deleted, department-scoped announcements are tombstoned for sync.
- User moves department: announcements of the old department disappear from their feed at the next sync (tombstone-like rule via visibility; implement as: feed query is recomputed per caller; a `fullResync` flag is set when the caller's department changed — store `visibilityGeneration` in the response; client resyncs on change).
- A head posts company-wide → 403 with `org_ann_not_allowed`.
- An org admin posts to a hidden department → allowed.
- 4,000-code-point body with emoji, RTL; link detection only http/https, shown with the host; tap shows a confirmation "Open this link in your browser? host".
- A pinned announcement expires → unpinned automatically (expiry wins).
- Pin limits reached → 409 with the sentence naming which ones are pinned.
- Retention purge while a client is paging → page returns fewer rows; no error.
- Time zone/DST for expiry in the console (explicit "in your time zone (…)").
- 10,000 announcements in a department: browse is paged; initial sync capped; memory bounded.
- Hub clock wrong → server timestamps wrong; documented operator note; no client logic depends on it.
- Reconnect storm after a hub restart: clients fetch the changes feed with jitter (0–5 s); server feed query is indexed (test with 10,000 rows < 50 ms).
- A device offline for 6 months: `since` older than retained tombstones → `fullResync`.
- Two devices of the same person (not supported; one device per member) — behaviour undefined; nothing may crash.
- Announcement titles that duplicate: no uniqueness.
- Screen readers: the unread dot has a text equivalent.

## Beyond the minimum (REQUIRED for Plan A3; the contract's section 3 applies on top)

1. **Text hardening with golden tests shared by server and clients**: title and body limits count **Unicode code points** the same way everywhere (golden strings: emoji with ZWJ, surrogate pairs, combining marks, an exactly-at-limit and one-over case); control characters and bidi override/isolate characters are removed or neutralised by `AnnouncementText.clean`; zero-width and very long unbroken words render without breaking layout; HTML/markdown/script strings render as plain text on phones, desktop and in the console preview (assert the console builds nodes with `textContent`, never `innerHTML`).
2. **The changes feed is idempotent**: tests with duplicated, shuffled, gapped and repeated pages, a `since` value ahead of the server (restore from backup: epoch change forces a full resync), a delete arriving before its create, an edit of an item the client never saw. The client state after any such sequence equals the state after a clean full sync (property test).
3. **Search**: SQLite FTS5 operators and quotes in the user's query (`"`, `*`, `NEAR`, `OR`, a lone `-`) never cause an error or a different scope; results contain only announcements the caller may see (an outsider cannot find text of a hidden department's announcement); paging and ranking tested; 100,000 announcements measured (synthetic).
4. **Permission matrix as a table-driven test**: every role (org admin, head of the department, head of another department, employee, unenrolled, revoked) times every action (create company-wide, create department, edit own, edit other's, delete, pin, unpin, read, search) times own/other department. One assertion per cell, expected values written from the plan's table.
5. **Notifications**: title only (a test asserts the body text is absent from the notification payload and from logs), grouping and de-duplication, mute respected, Android 13+ notification permission denied path, tap routing from a cold start and from the background, desktop notification parity, no notification for your own post, no notification for items older than the last seen seq.
6. **Rate and size limits**: posts per poster per hour, request body cap, announcements per organisation cap with a plain error; a flood test proves the server stays responsive and the cap sentence is returned.
7. **Offline behaviour**: the app keeps the newest N announcements (N written in the plan or log), prunes older ones by a tested rule, never loses unread state on prune, shows cached items when the hub is unreachable with a "last updated" line, and shows the exact offline sentence when posting fails (nothing is queued).
8. **Relay frame `ann1`**: an old client ignores the unknown frame without closing the session (test with the old decoder); a new client treats the frame only as a hint and refetches the feed; a forged frame from another peer is ignored (it must come from the hub session only).
9. **Console preview equals the phone**: one shared golden (same input, same visible text and line breaks) used by a console test and a client test.
10. **Retention and expiry**: expiry job with injected time; expired items disappear for readers and from search; the optional hub-wide retention setting is validated (bounds) and documented; deletion also removes the search index row (test).
11. **Accessibility of the reader and composer**: reading order, large font, a "posted by" line for screen readers, the unread badge read out, composer character counter announced at limits.
12. **Security documentation**: announcements are readable by the hub operator and admins (stated plainly in `docs/security.md` and in the composer footer), the threat rows for impersonation of a poster, department spoofing and notification content.

### 2026-10-15 — Plan A3 Explain-Back (quality contract section 2, no code yet)

#### 1. What the phase must achieve and why
Plan A3 implements organization announcements: one-way broadcast messages with a title and plaintext body stored unencrypted on the hub (ADR-138). Org admins can post company-wide or to any department; department heads can post only to their assigned department(s); regular employees can only read and search. The server provides a migration (component "announcements", version 1), SQLite FTS5 full-text indexing, strict input sanitization (`AnnouncementText.clean`), authenticated REST routes for devices and console admins, an idempotent changes feed (`since=<seq>`), optimistic concurrency on edits (`expectedSeq`), pin limits (max 3 org, max 3 dept), optional expiry/retention cleanup, capability-gated live WebSocket push via `RelayFrame.AnnouncementEvent` with `ann1` feature negotiation, and console management UI with live rendering preview. On the client side, it adds DTOs, Room schema step 17 with `HubAnnouncementEntity` and `HubAnnouncementStateEntity`, `HubAnnouncementsApi`, and repository operations in `FlashChatRepository` with typed error handling.

#### 2. Files to touch / create and 3 most similar classes read

#### 3. Five ways this phase can fail
1. **Races & Concurrency**: Simultaneous edits colliding. Guarded by atomic SQLite transactions and `expectedSeq` optimistic locking (returning 409 Conflict with current item).
2. **Wire & Backward Compatibility**: Older clients crashing on new frame. Guarded by capability gating `ann1` in `Hello.features` and forward-compatible codec ignoring unknown frames/fields. Old hubs communicating with new clients guarded by feature discovery and `org_ann_unsupported`.
3. **Security & Scope Leaks**: Department head posting or viewing cross-department or hidden department announcements. Guarded by enforcing department match against authenticated session/cert, not request body, and filtering inside SQL. Announcements explicitly stored in plaintext (ADR-138) with no false encryption claims.
4. **Scale & FTS injection**: Malformed search queries breaking FTS5. Guarded by parameterization and escaping of FTS operators, query length bounds (<= 64 chars), and SQL pagination.
5. **Platform & Unicode Differences**: Code-point counting vs Java string length (surrogate pairs / emoji). Guarded by Unicode code point counting, NFC normalization, stripping bidi overrides.
