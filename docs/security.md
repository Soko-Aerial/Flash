# Flash Security Model

**Status:** Living document. Established 2026-08-22 during Phase P2 (`docs/core-upgrade-plan.md` §C2). Update whenever the security surface changes.

## 1. Threat model (v1 scope)

| Asset | Threat | Mitigation | Where |
|---|---|---|---|
| Message content on disk | Device theft / forensic extraction | SQLCipher full-database encryption; key wrapped by AndroidKeyStore (wiring lands C7) | `:core:persistence` C1 |
| Message content on the wire (same LAN) | Passive sniffing / active MITM | TLS 1.3 with self-signed certs + TOFU fingerprint pinning (C4, planned) | `:core:network` C4 |
| Message content beyond a relayed/mesh hop (future, D5) | Malicious relay | Frame-level E2E over TLS (this phase, C2.7) — payload opaque to any intermediary | `:core:security/crypto/E2eFrameCodec` |
| Identity theft across reinstalls/backups | Cloned identity | Identity key non-exportable in AndroidKeyStore; excluded from Android backup (manifest flag at app layer) | `KeystoreFlashCrypto` |
| Evil-twin peer impersonation | MITM on first connection | Pairing v2 (ADR-042): commit-then-reveal nonces; the 6-digit code covers both TLS-pinned identity keys, both ephemeral keys and both nonces, so a MITM cannot force a match (≈10^-6). Each side refuses a pairing fingerprint that is not the key TLS pinned for that connection. Inbound TLS requires the client certificate (audit S1). Mismatch after pinning = hard fail + `PeerKeyChanged` | `PairingV2`, `PairingSessionStateMachine`, `TofuPinVerifier`, `WsFlashNetwork.inboundIdentityFailure` |
| Legacy trust flag abuse | Old "trusted" flag silently becoming a crypto pin | Legacy migration writes `LEGACY_UNBOUND_FINGERPRINT`; TOFU re-prompts on first contact instead of trusting blindly | `LegacyTrustMigration` |
| Group membership forgery / roster poisoning | Legacy groups (≤ 6, unchanged) have unsigned rows; V1a (2026-09-29) closed the cheap forgeries (F-1, F-2, F-4, F-5). **v2 groups (ADR-044 V1, built 2026-09-30, device check GT-02 owed):** an owner-signed charter, per-member owner-signed certs and per-message author signatures, so a paired member can no longer rewrite the roster, forge another member's message or take the group over. Vouched trust (groups of 20) is V2, not built | `docs/group/v0-threat-review.md`, `docs/group/v1-signed-membership-plan.md`, section 8 below |
| Group files between members that never paired; joining a group with its id + secret (**PROPOSED 2026-10-04, nothing built**) | Forged cancels and announcements, stolen or leaked invites, relayed proofs, removed members coming back | Signed swarm statements checked against the origin key; the group gate read per frame; a proof bound to both TLS keys; a rotation on every removal; an invite or pairing as the only charter roots. Full rows in section 10 | ADR-070 to ADR-075, section 10 below |
| Timing side channels on comparisons | Fingerprint/code oracle | All secret-material comparisons via `MessageDigest.isEqual` (constant-time) | `FlashFingerprint.constantTimeEquals`, `NumericComparisonCode.hashesEqual` |

Out of scope for v1: anonymity / metadata protection beyond the local network, forward secrecy across session-key compromise (see §4 Rekey), post-quantum.

## 2. Identity (C2.1–C2.3)

- **Identity key:** ECDSA P-256, alias `flash_identity`, generated in AndroidKeyStore. Purposes SIGN|VERIFY only, digest SHA-256 only. StrongBox-backed when available (API 28+, literal feature string `android.software.keystorestrongbox`), silent TEE fallback on `StrongBoxUnavailableException`/`ProviderException`. Biometric-enrollment invalidation disabled so identity survives fingerprint re-enrollment.
- **Certificate:** self-signed X.509 generated by the platform as part of keystore keypair creation (`setCertificateSubject/NotBefore/NotAfter`) and retrieved via `KeyStore.getCertificate(alias)` — zero extra dependencies (BouncyCastle rejected: multi-MB APK cost for capability we do not use, since trust comes from fingerprint pinning, not chain validation).
- **Fingerprint:** SHA-256 of the X.509-encoded identity public key (decision D3), displayed uppercase colon-grouped hex.

## 3. Pairing & TOFU (C2.5–C2.6; protocol v2 per ADR-042)

### 3.1 Current: pairing v2 (2026-09-23)

```text
I -> R : PAIR_REQUEST  v=2, fp_I, epk_I, commit_I = H(commit ‖ fp_I ‖ epk_I ‖ N_I)   (N_I hidden)
R -> I : PAIR_NONCE    fp_R, epk_R, N_R                                        (R reveals first)
I -> R : PAIR_REVEAL   N_I                   — R checks commit_I; only now does a code exist
code   = H(code ‖ fp_I ‖ fp_R ‖ epk_I ‖ epk_R ‖ N_I ‖ N_R) mod 10^6   (role-ordered, length-prefixed)
R -> I : PAIR_ACCEPT   — R's user compared both screens
I -> R : PAIR_CONFIRM  codeHashHex
R -> I : PAIRED        fp_R, epk_R — must equal what the code covered
```

- **Binding to the transport:** each side requires the peer's pairing fingerprint to equal the SPKI
  fingerprint TLS pinned for that peer on this connection (`FlashTrustStore.getPin`). Both are SHA-256
  of the same identity key's X.509 SPKI encoding (Android keystore alias / desktop `PersistedFlashCrypto`).
- **Session key:** ECDH over `epk_I`/`epk_R`, which the code covers, so a substituted ephemeral key
  shows up as two different codes.
- **v1 peers are refused** (`peer-update-required`); a v1 hello (no `v` field) makes the initiator tell
  the user to update the other device. Existing v1 pairings stay trusted but are shown **Not verified**
  (`FlashTrustStore.isVerified`) with a **Verify** action that runs v2.
- Failure reasons (all fail closed): `identity-mismatch`, `commit-mismatch`, `paired-material-mismatch`,
  `code-hash-mismatch`, `peer-update-required`, `invalid-fingerprint`.

### 3.2 SUPERSEDED: pairing v1 (kept for history — why it was replaced)

v1's code was derived from the two static fingerprints alone. With no nonce and no commitment, a MITM
could grind keys until both screens matched (~10^6 key generations). The code also covered neither the
ephemeral keys (the session key) nor the TLS-authenticated identity, so a relay needed no grinding at
all. Audit 2026-09-23, S2. The v1 flow was:

1. Initiator sends `PAIR_REQUEST{requestId, deviceId, name, model, fingerprintHex, ephemeralPubKey}`.
2. Responder consents → `PAIR_ACCEPT`. Both sides derive the **6-digit display code** identically: `SHA-256(lexicographicallySorted(fingerprintA, fingerprintB))`, first 5 bytes big-endian mod 10^6, `%06d` — symmetric by construction (Bluetooth SSP numeric-comparison precedent), so role order never changes the code.
3. Initiator proves it derived the same code with `PAIR_CONFIRM{codeHashHex}` (hash, not the code itself); responder verifies constant-time. Mismatch ⇒ session `Failed` (protocol violation), never `Expired`.
4. Responder completes with `PAIR_PAIRIED{fingerprintHex, ephemeralPubKey}`; both sides reach `Confirmed` and the peer is pinned in `RoomTrustedStore` with its fingerprint.
5. Timeouts are engine-owned (`PairingTimeouts`: request expiry 30 s default mirroring UI-032 countdown, per-side decision window configurable). Expiry is **neutral** (`Expired ≠ Failed`) per profile-ui.md semantics.

TOFU policy (`TofuPolicy.evaluate`): no record ⇒ `FirstConnect` (consent prompt); presented fingerprint matches pin ⇒ `Match`; anything else — including a *missing* presented fingerprint when a pin exists — fails **closed** (`Mismatch`). Revocation clears the pin; next contact re-prompts.

## 4. Frame-level E2E (C2.7, decision D4)

- **Key agreement:** ephemeral software ECDH P-256 keypairs exchanged during pairing (AndroidKeyStore `PURPOSE_AGREE_KEY` exists only since API 31 < our minSdk 24 — ephemeral keys are memory-only by design and need no hardware backing).
- **Derivation:** HKDF-SHA-256 (RFC 5869, extract-then-expand, info binds `"flash-e2e-v2"` context) over the shared secret → 32-byte AES-256 key.
- **Wire format:** `[12-byte random nonce | AES-GCM ciphertext+tag]`, AAD = protocol-version string, so frames cannot be replayed across protocol versions.
- **Nonce discipline:** 96-bit random nonces from `SecureRandom`; hard limit 2^32 encryptions per session key (NIST SP 800-38D random-nonce bound) — unreachable in practice at P2P message rates, enforced conceptually by per-pairing-session keys.
- **Rekey policy:** new ephemeral exchange on each pairing; automatic periodic rekey is **deferred to the mesh/relay workstream (D5, post-v1)** — direct TLS sessions already rotate keys at the transport level.
- Layering: E2E encrypts `FlashEnvelope.payloadJson` *inside* TLS. TLS protects the hop; E2E makes payloads opaque to any future relay.

## 5. Known gaps / debt

- Keystore path and E2E codec are JVM-tested via `SoftwareFlashCrypto`; **device verification of the Keystore impl is pending** (backlog item).
- `PAIR_DECLINE` has no wire frame yet — declining resets locally; peer sees expiry instead (documented in KDoc, wire encoding lands C4/C6).
- Backup-exclusion manifest flags belong to the app layer (C7 wiring).
- No forward secrecy across device compromise of a long-lived session key yet (accepted for v1 direct-P2P scope).

## 6. Binary Chunk End-to-End Encryption (`SecureBinaryFrameCodec` / `FSEC`)

File transfer chunk frames and receiver acknowledgements support binary-level payload encryption:

- **Envelope Header (22 bytes)**:
  - Magic (4 bytes): `FSEC` (`0x46, 0x53, 0x45, 0x43`)
  - Version (1 byte): `0x02` (Protocol Version 2)
  - Envelope Type (1 byte): `0x01` (`AES-256-GCM`)
  - Nonce (12 bytes): Cryptographically secure random nonce (`SecureRandom`)
  - Length (4 bytes, Little-Endian): Length of following ciphertext + 16-byte GCM authentication tag
- **Ciphertext**:
  - Algorithm: AES-256-GCM (128-bit authentication tag)
  - Key: 32-byte pairwise session key derived during pairing (HKDF-SHA256 over ECDH shared secret)
  - AAD: `"flash-chunk-v2"` (binds ciphertext to the binary chunk transport protocol version)
- **Opportunistic Execution**:
  - Outbound transfers (`StreamChannel` via WebSocket fallback and dedicated Data Channels): If `sessionKey != null` for the target peer, the entire binary frame is encapsulated in an `FSEC` envelope. If unpaired, plain `FLSH` binary frames are transmitted.
  - Inbound frames (`handleInboundBinary`): Frames starting with `FSEC` magic are checked for session key availability. Decryption fails closed if no key exists or if tag verification fails. Replies (ACK batches, Completion frames) are automatically encrypted with the same session key.
  - State reflection: `FlashTransfer.isEncrypted` truthfully surfaces whether file chunks are encrypted.

## 7. Wire-Level Transport Security (TLS 1.3 & TOFU Discovery Pinning)

Mesh WebSocket transport provides wire-level encryption (`wss://`) with Trust-On-First-Use (TOFU) pinning:

- **Certificate Generation**:
  - **JVM / Desktop**: `FlashCertMaker` generates self-signed X.509 certificates with EC P-256 keys using BouncyCastle PKIX, exporting in-memory PKCS12 key stores for `KeyManagerFactory`.
  - **Android**: `KeystoreFlashCrypto.selfSignedCertificate()` utilizes `AndroidKeyStore` with ECDSA P-256 to produce platform-native self-signed X.509 certificates.
- **TOFU Pinning (`TofuPinVerifier`)**:
  - During TLS handshake, peer certificates are extracted.
  - The SHA-256 fingerprint of the peer's public key is computed via `FlashFingerprint.fingerprint()`.
  - If no pin exists in `FlashTrustStore`, the fingerprint is recorded (TOFU).
  - If a pin exists, the incoming certificate's fingerprint is verified in constant time (`MessageDigest.isEqual`). Any mismatch fails closed immediately with an `SSLException`, preventing MITM attacks.
- **Manual-IP dial — deferred binding (ADR-040)**:
  - A dial that cannot name its peer ("Connect by IP" to a device discovery never saw) has no
    `expectedDeviceId`, so the handshake accepts the leaf and records its fingerprint instead of
    failing closed.
  - `connectManual` then runs the **same** `isPinned(peerDeviceId, leaf)` check once
    `FLASH_WS_HELLO` names the peer, and closes the connection before registration if it fails.
  - Opt-in per dial (`deferPinWhenDeviceIdUnknown`, default `false`): discovery-driven dials,
    redials and both server paths are unchanged.
  - Accepted exposure: our own HELLO (device id + friendly name — the same fields mDNS broadcasts)
    reaches the dialed address before binding. No message, file or key material does.
- **Engine Integration**:
  - Handled via `TlsOptions` across `WsFlashNetwork`, `JvmWsFlashNetwork`, `WsTransferClient`, `DesktopEngine`, `Flash.kt`, and `DiscoveryEngineHolder`.

## 8. v2 groups: signed membership and signed messages (ADR-044 V1, 2026-09-30)

Wire and byte layouts: `docs/protocol.md` "v2 groups". Design: `docs/group/v1-signed-membership-plan.md`. Built and unit-tested
(`SignedGroupsTest`, `GroupSignatureRulesTest`, codec and migration tests); **not yet run between real devices (TEST-BACKLOG GT-02)**.

**What it guarantees, for a v2 group only:**
- The group id is derived from the owner's key (`g2-` + hash of key and nonce), so an id names exactly one possible owner. Nobody can
  pre-create or re-own an id.
- Only the owner adds a member; a member can only sign their own leave. A cert binds a device id to a key the *receiver's own pin*
  vouches for (or the receiver's own key, or the owner's), so the owner cannot slip a key of its choosing under another member's id.
- Every message carries its author's signature. A relay (catch-up) keeps the true author, so a member cannot plant text under someone
  else's name and delete authority follows the real author (ERROR-082 / F-9, fixed for v2).
- Legacy membership frames for a `g2-` id are dropped; a v2 group never goes back to legacy; old clients are never admitted.
- Receiver-side CPU is bounded: only a cert that would replace what is stored is verified, at most 120 verifications per peer per
  minute, bundles capped at 84 certs (20 active + 64 tombstones since V2; 70 before).

**Known limits (accepted for V1):**
- ~~Every v2 member must still be paired with every other member.~~ **Lifted by V2** (section 9): members need to be paired with the
  owner only, and a v2 group holds up to 20.
- The owner is the single point of trust and failure: no ownership transfer, no rename, no owner-side remove UI. A lost owner device
  freezes the roster.
- Creating a group with an invitee that has no live session yields a legacy group (its level is unknown). An invitee that advertises
  level 2 but whose session key is missing or does not match its pin makes create/add fail, **never** a silent legacy fallback.
- Sync does not re-deliver messages written by a former member (a relayed message must name an active author).
- A relay that never saw a newer tombstone can show an outdated active cert; bounded by the full-roster reconcile on every session-up.
- No forward secrecy or per-sender keys: a removed member keeps what they received.
- Signing cost on the target phones is unmeasured (StrongBox sign latency, ECDSA verify per message): owed as a measurement (TEST-BACKLOG).


## 9. Vouched trust: members who never paired with each other (ADR-044 V2, 2026-09-30)

Design and slices: `docs/group/v2-vouched-trust-plan.md` (E1 to E6). Built and unit-tested (`TrustStoreGroupVouching` tests for both
stores, `SignedGroupsTest`, `CallCoordinatorSecurityTest`, the dial-budget and presence/ECO tests); **not yet run between real devices
(TEST-BACKLOG GT-03; GT-02 for V1 is also still owed)**.

**What it changes, for a v2 group only.** Everyone pairs with the **owner**; the owner's signed cert for a member is the introduction.
A member the receiver never paired can then chat in that group and join its group calls. They cannot do anything else: no 1:1 chat,
no files (group attachments are paired-only in both directions), no 1:1 calls, no push-to-talk, no pairing rights.

**How the pieces fit:**
- **Pin sources.** Each trust store derives `PinSource` (PAIRED > VOUCHED > TOFU) and keeps one new thing, the set of group ids that
  vouch for a device (`vouch_<id>` on Android, `vouch.<id>` on desktop). `VouchRules` is the single copy of the rule; a vouch installs
  the pin **before** the peer connects, so TLS needs no change (`TofuX509TrustManager` still only asks "is this key pinned for that id?").
- **Precedence.** A vouch never overrides a paired pin (`CONFLICT_PAIRED`, cert refused). It replaces an unverified first-use pin, which
  is what defeats a device that connected first under a member's id. Two groups that vouch different keys for one id keep the first
  (`CONFLICT_VOUCHED`). Blank input is `INVALID`.
- **The group gate does not trust the pin store.** `isGroupPeerTrusted(groupId, peer)` = paired, **or** an active member of the stored
  verified roster **and** the peer's live TLS key equals the cert key. So a TOFU session an attacker opened before the vouch replaced
  its pin still is not trusted in the group, and knowing a member's id is not enough to speak as them.
- **Side effects are ordered.** Vouching is the first side effect of accepting a bundle, after every ignore check, so a bundle that is
  ignored leaves no pin behind. Leaving a v2 group, or an owner tombstone, revokes the vouch (deleting a chat without leaving does not, see the limits); a paired pin is never touched
  by a group operation, and unpairing a vouched member keeps the pin while a vouch record exists.
- **Owner remove.** `removeGroupMember` (owner only, next `seq`, signed tombstone) revokes the removed member's vouch on every device
  that had one. The members sheet offers it (a **Remove** action per row, never the owner's own, shown only when the repository
  says `canRemoveMembers`, i.e. this device owns a v2 group) behind a confirmation whose copy says a removed member keeps what they
  already received. Unit-tested; **not device-verified (TEST-BACKLOG GT-03 step 7)**.
- **What the other devices do (removal ripple, ERROR-083).** A member that hears of the removal drops the vouch and the row; a member that
  reconnects later to a removed device that was offline hands it the owner's tombstone (`removalNoticeFor`, verified by the removed
  device against the owner key in the charter). A device that is out (removed or left) ignores every bundle except an invitation back,
  withdraws the vouches when it verifies its own tombstone, refuses to send, store group traffic or place calls, and its screen shows a
  notice instead of the composer. Group calls use `isGroupCallPeer` (trusted in the group **and** an active roster row), not the plain
  gate, so a removed member that is still paired cannot ring or join. Re-adding is the ordinary owner Add members flow and lifts all of it.
- **Visible to the user.** A member the local device never paired shows "Added by <owner> · not verified" and a **Verify** action that
  runs ordinary pairing (`connectManual` + `beginPair`); pairing turns the member PAIRED and the label disappears.

**Accepted limits (V2):**
- The owner is still the single point of trust and failure. **A lying owner can vouch a key it controls** for a name it chooses; the
  "Added by" label and Verify mitigate this, they do not prevent it. Trust is one hop deep by design (a vouched member's vouches count
  for nothing).
- A removed member keeps what they already received (no per-sender keys, no forward secrecy). Removal is also **eventually consistent**:
  a member that has not heard of it yet keeps sending to the removed device, and a modified removed client could read that until the
  member converges from the owner or another member.
- Vouched members get no files in either direction.
- An already-established group **call** leg is not re-checked: a member removed mid-call stays connected until the call ends
  (pre-existing behaviour of call legs, unchanged by V2).
- Deleting a v2 chat **without leaving** keeps its member rows and vouches, and a stale-row rejoin after a delete is a latent V1
  issue that V2 inherits. Leaving is the clean path (it revokes everything).
- An attacker's already-open TOFU session under a vouched id stays a 1:1 peer (review finding F-8, adjacent debt); it is not group-trusted
  because its key differs from the cert's.
- A bundle carries at most 20 active certs and 64 tombstones (84). The 64 is V1's cap, unchanged; what happens to a group that has
  removed more members than that was not designed in V2.
- Unmeasured: a 20-member roster's verification cost and the mesh's session count on phones (MEAS-08, SC-01, SC-02).

## 10. Group swarm and membership by group secret (ADR-070 to ADR-075, PROPOSED 2026-10-04, nothing built)

Threat rows written in SW-0 of `docs/transfer/GROUP-SWARM-IMPLEMENTATION-PLAN.md`, before any code. Each row names the invariant that answers
it: INV-x is in the plan's section 5.6, GINV-x in its section 5.7. Wire details: `docs/protocol.md` "Group swarm wire FSW1 v1" and "Group
membership v1". **None of this exists yet; section 9's limits stay true until GM-5 and SW-8 land.**

### 10.1 The swarm

| Threat | What an attacker tries | Mitigation | Invariant |
|---|---|---|---|
| Forged cancel | A member, or anyone with a session, sends `CANCEL` to stop a file for everyone | A tombstone counts only if it verifies against the origin key stored with the announcement, under its own tag `flash-swarm-v1/cancel` | INV-6 |
| Forged announcement | A member announces content under another member's name, or a root that does not match the file | `rootSig` by the origin's roster key over group, message, origin, root, size, name and type; a `swarm=1` announcement that fails is dropped with no bubble. Pieces are then checked against the manifest, and the manifest against the root | INV-6, INV-2 |
| Cross-group oracle | A member of group G asks for a root it learned in group H, to learn whether this device holds it | Content is served in G only if this device holds its announcement in G; otherwise `REJECT(UNKNOWN)`, the same answer as for content that does not exist | INV-8 |
| Request flood | A member asks for everything at once to exhaust upload, memory or battery | At most 64 pieces per `REQUEST`, a per-requester byte budget, serve slots by performance mode, `REJECT(BUSY)` | INV-12 |
| Corrupt piece | A faulty or hostile member serves wrong bytes; or this device's own disk or source changed | Every piece is hash-checked before it is written and re-hashed before it is served; the whole file is checked at the end (ADR-068); a source of bad pieces gets strikes and is dropped for that transfer | INV-2 |
| Removed member | A removed device keeps fetching or serving | The gate is read for every request; no cached answer outlives a membership change | INV-3, GINV-6 |
| Replayed tombstone | An old, valid tombstone is replayed to cancel a later re-send of the same file, or another member's announcement of the same bytes | A tombstone cancels only the announcement `(groupId, messageId)` it names, and verifies only against that announcement's origin key | INV-5, INV-6 |
| Hostile manifest sizes | A manifest claims a huge piece count, many fragments or oversize fragments | At most 16,384 pieces, 9 fragments of 64 KiB, piece size 64 KiB to 1 MiB; a manifest is used only after its root is recomputed and its size matches the announcement | INV-12 |
| Malformed-frame flood | A peer sends broken FSW1 frames to burn CPU or to get the session dropped | The decoder never throws; after 3 malformed frames in a minute that peer's FSW1 frames are ignored for 10 minutes; the session (chat, calls) is never dropped for it | INV-12 |
| Storage exhaustion | A member announces a very large file | Nothing is fetched before Accept unless auto-accept is on (and then only up to the device's size limit); the free-space gate of ADR-069 applies at Accept and before each start | ADR-069 |

### 10.2 Membership by group id + secret

| Threat | What an attacker tries | Mitigation | Invariant |
|---|---|---|---|
| Leaked invite | Someone outside the group obtains the link | Under `APPROVE` (the default) the secret alone puts no key into the roster: an admin sees the request and decides. Under `OPEN` the holder is admitted until a removal and the rotation that follows it. "Change group code" rotates on demand | GINV-5, GINV-4 |
| Relay during the proof | A man in the middle holds two TLS sessions and forwards the proof messages | The MACs cover both live TLS key fingerprints, which differ on the two relayed sessions | GINV-7 |
| Replayed or reflected proof | An old MAC is replayed, or the responder's MAC is sent back as the initiator's | Fresh 16-byte nonces from both sides, role bytes `I` / `R`, a one-shot state machine, constant-time comparison | GINV-7 |
| Offline guessing of a weak secret | An observer records a challenge MAC and guesses the secret offline | The app generates 256 random bits; there are no typed codes (D3) | GINV-1 |
| Membership oracle | A stranger who knows a group id asks devices to prove it, to learn who is in the group | A device that does not hold the group still answers with a random challenge and then a plain failure; it says "stale" only after a valid older proof or to an active roster member | GINV-7 |
| Stale epoch | A peer claims a newer or older epoch to make others change state | An epoch number is a claim: rotations are learned only from admin-signed notices. A member that missed a rotation keeps chatting (O-13) and asks for the secret | GINV-2, GINV-4 |
| Removed member rejoins | A removed device uses its old invite, or asks to join again | Every removal rotates the secret, so the old invite fails the proof; `OPEN` never auto-approves a tombstoned key; its tombstone keeps it out of the gate | GINV-4, GINV-5, GINV-6 |
| Secret handed to a removed device | A member that has not yet heard of a removal hands the new secret to the removed device | The new secret exists only alongside its notice, and the notice names the removed ids: no device hands a secret to an id named in any stored notice, and the handover checks the gate at that moment | GINV-1, GINV-4 |
| Forged or replayed rotation notice | A member forges a notice to lock others out, or replays an old one | A notice counts only if an admin signed it (tag `flash-grot-v1`); epochs only grow; for one epoch the smaller rotation id wins | GINV-4 |
| Handed secret that does not match | A peer hands a wrong secret to split the group | The receiver stores it only if it matches the commitment in a valid notice for that epoch | GINV-4 |
| Join-request flood | Someone floods admins with join requests | A request needs a passed proof (only invite holders can send one); failed proofs are rate-limited per peer; requests are kept once per subject key and expire after 7 days; admin notifications are collapsed per group | GINV-5 |
| Unknown group pushed onto a device | A peer sends a valid bundle for a group this device never asked for | A charter is trusted only through pairing with its owner or an invite this device accepted for exactly that group id | GINV-3 |
| Impostor at the inviter's id | A device answers the first dial under the inviter's id | The invite carries the inviter's key fingerprint, installed as a group-scoped vouch before the dial, so TLS refuses any other key and nothing is pinned on first use | GINV-3 |
| Secret leaked through logs or backups | The secret ends up in logcat, a crash report, a notification or a cloud backup | It is stored only in the encrypted database (desktop protection checked in GM-2), excluded from backups, and never logged: logs show the group id and epoch only | GINV-1 |
| Group-only peers without app-layer chunk encryption | A passive or active attacker on the LAN reads file chunks between members that never paired | TLS 1.3 to the certified key protects them. There is no pairing session key between such peers, so no `FSEC` envelope, and no group session key is planned. **Accepted limit**, the same as for vouched members today | GINV-2 (identity), accepted |
| 1:1 escalation | A peer that is only a group member tries 1:1 chat, a 1:1 call, push-to-talk or pairing rights | `isTrustedPeer` still gates every 1:1 feature; group membership grants nothing outside the group | GINV-8 |

**Accepted limits (in addition to section 9):** no forward secrecy; a removed member keeps what it received; removal is eventually
consistent; under `OPEN` a leaked invite admits its holder until the next rotation; a lying admin can approve a key it controls.

## Inbound transfer identity and completion (ADR-099, ERROR-125, 2026-10-08)

- A transfer id belongs to the peer that first offered it. Control frames (`pause`/`resume`/`cancel`), a repeated `FILE_START` and `CHUNK` frames for that id from any other peer are ignored and logged. Sender-side `ACK`/`COMPLETE` frames are **not** yet bound to a peer (needs a `:core:transfer` signature change; follow-up).
- Transfer ids that change under `FlashPathSanitizer.sanitize` (for example `..`, `.`, ids with `:` or path separators), or that differ only by case from a live id, are refused with a cancel, because the sink directory is derived from the sanitized id.
- If flushing or closing the received file fails, the transfer is accepted only when the whole-file SHA-256 from the sender matches; with no hash, or a mismatch, it fails and the partial file is deleted. A chunk-verified-only result never overrides a failed flush.
- Swarm announcements are validated before any model object is built: `root` must be 64 lowercase hex characters, the piece size a power of two inside the allowed range, and the total size within 1 byte to 16 GiB. An invalid announcement is dropped with a WARN that logs only lengths.
- File names are capped at 120 code points and 200 UTF-8 bytes on a code-point boundary with the extension kept; Windows device names (CON, PRN, AUX, NUL, CONIN$, CONOUT$, COM0-9, LPT0-9 and the superscript forms) are neutralised with or without an extension.
- A failure to unwrap the database passphrase never mints a new one unless the Keystore key is permanently gone; a transient error is retried once and then surfaced, so chat history is not quarantined by a flaky Keystore.


## Enterprise hub trust model (ADR-107, ADR-109, ADR-110; 2026-10-12)

Scope: the organisation hub (`:server`) and the clients that enrol with it. The wire and signing bytes are specified in
`docs/protocol.md` "Hub relay wire v2 and hub REST contract v1"; the findings behind this section are in
`docs/audit/2026-10-12-server-hub-audit.md`. Everything below is unit-tested, contract-tested and NOT yet device-verified (`HUB-*` in
`docs/testing/TEST-BACKLOG.md`).

### Trust anchors and who may sign what

- **Organisation root key**: signs delegations and (optionally) revocation lists. Clients pin its SHA-256 (`serverId`, from the invite's
  `root=`); the hub holds only the public key at runtime. A client that cannot pin a root (blank `root=`) refuses to enrol.
- **Hub delegated key**: certified by a root-signed `DelegationCert` with a scope set (`enrol:member`, `enrol:dept_admin`, `enrol:admin`,
  `revoke:member`), a validity window and a device cap. It signs device certificates. Scopes use one wildcard rule (exact, `*`, `prefix:*`);
  `admin` is never granted by a wildcard.
- **Device key**: generated on the device, never leaves it. Its public half is certified by the hub key. The device proves possession of it
  at enrolment, at every relay connect and at every REST login.

### What a connection must prove

1. The hub's CHALLENGE names a `serverId`; a client pinned to another realm refuses to answer (a rogue hub gets no signature).
2. The device signs (serverId, serverNonce, clientNonce, deviceId, certSerial) under a domain tag: bound to the audience (no cross-organisation
   replay), to a fresh single-use nonce from the hub (no replay), to the client's own nonce (a hostile hub cannot pre-compute), and
   to a certificate serial (a stolen signature cannot be paired with another certificate). Fields are length-prefixed (no `a|bc` ambiguity).
3. The chain verifies against the pinned root with a 60 s clock tolerance at both ends and the closed role set.
4. The sender of every relayed message is the authenticated principal; a client-supplied sender is not read (SEC-02).

### Enrolment

The invite token only authorises a request; it does not authorise a key. The device signs (token, deviceId, subjectPublicKey, serverId) and
the hub verifies that BEFORE it spends the token or a quota slot (a bad proof does not burn a good invite). The issued leaf is clamped to
the delegation window (`validFrom = max(now - 10 s, delegation.validFrom)`, `validTo = min(now + 7 days, delegation.validTo)`), so a
certificate never outlives or predates the authority that issued it (SEC-18). The client verifies the response chain against the pinned
root and the invite fingerprint before it stores anything.

### Revocation

Signed monotonic `RevocationList` (`flash-revocation-v2`): certificate serials, device ids and delegation serials. Only the root may revoke a
delegation; a delegate holding `revoke:member` may revoke devices. The check order puts revocation before expiry so a revoked, expired
certificate reports `ERR_REVOKED`. The chain verification (`checkChain`) and the handshake honour a list. **Since 2026-10-13 (ADR-113) the hub builds, root- or delegate-signs, persists and serves the
list** (`GET /api/v1/revocations`, bearer), revokes by serial and by device id, kills the device's bearer at once (`BearerTokenStore.resolve` re-checks every use),
removes it from the directory and kicks its relay socket (`onRevoked`). A revoked id cannot re-enrol until an administrator unrevokes it, and the old
serials stay revoked. The remaining gap is the CLIENT: it does not yet fetch or honour the list (HUBA-14).

### Errors and logging

A rejection on the wire or REST carries a fixed sentence and a code from `HubErrorCodes`, never exception text or a value from the request
(SEC-16 for the hub's own routes; the generic StatusPages handler still echoes `cause.message`, Phase 2). Logs carry device ids, serials and
codes; never a private key, token, nonce, signature or certificate body. Bearer tokens are 32 random bytes, valid 15 minutes; the hub keeps
only their SHA-256.

### Offline root, delegation and hub keys (ADR-111, 2026-10-13)

The organisation root key is created and used OFFLINE with `server keytool` (encrypted file, owner-only; the pass-phrase never touches the hub). The hub
holds only its delegate key and a root-signed, time-limited delegation with explicit scopes and a device cap. Consequences an operator must know:
a stolen hub can enrol devices only until the delegation expires or is revoked (revoke the delegation serial with a root-signed list); losing the root key
means re-enrolling the organisation; the hub refuses to start with a root key in its data directory (except the loud dev flag); a corrupt delegate key is
an error, never silently replaced; with no valid delegation the hub only serves its admin console (awaiting-delegation mode). The delegation expiry is
logged at 14 and 3 days left.

### Transport, listeners and the admin surface (ADR-114, ADR-115, 2026-10-13)

- TLS: `proxy` (hub behind a TLS terminating reverse proxy), `self` (self-signed P-256 certificate kept across restarts, fingerprint logged) or `none`
  (insecure opt-in). Invites and QR codes carry `https://` only; the hub refuses to create an `http://` invite unless insecure mode is on.
- The admin console and API live on the management listener (loopback by default); the public port serves no `/admin`. Reach it with an SSH tunnel
  or an authenticated proxy. Cookies are `__Host-` Secure, HttpOnly, SameSite=Strict.
- Admin sign-in: PBKDF2-HMAC-SHA256 600 000 iterations, TOTP with single-use steps, hashed recovery codes, persisted lockouts keyed by user and address,
  attempts reserved before verification, equal work for unknown users, sessions hashed at rest (30 min idle, 2 h absolute, 5 per admin).
- Dangerous admin actions need a step-up confirmation signed by the admin's own enrolled device and bound to the action and target; CSRF needs the
  session-bound header plus a same-origin check. Every admin and key event goes to a persisted, hash-chained, delegate-signed audit log
  (`audit/verify` recomputes it). Remaining limit: the chain is anchored only by the delegate key on the same host, so export the head off the box.
- Abuse limits: token buckets per client address on enrol, auth and the directory; forwarded addresses are believed only from `FLASH_TRUSTED_PROXIES`;
  bodies over 64 KiB are refused; no regex JSON in any security path; the setup token lives in an owner-only file and is not printed in production.
- Docker: non-root, `.dockerignore` keeps keys and keystores out of the build context, HEALTHCHECK through `server healthcheck`, only 8443 exposed
  (image not built by the author: `HUBA-10`).

## Hub admin console (ADR-125, 2026-10-13)

The administrator's browser console (`docs/ui/hub-admin-console.md`) is static files served by the hub itself.

- **No injected markup.** Every page is built with `document.createElement` and `textContent`; there is no `innerHTML`, `eval`, inline script, inline handler or style attribute. A test scans every console file for forbidden patterns, and another asserts the CSP and the other headers on every asset and error response under `/admin`, `/enroll` and `/enroll-assets/` (`AdminConsoleWebTest`). The CSP allows only same-origin scripts, styles, images (plus `data:` and `blob:`), fonts and connections, and forbids framing, forms to other origins and a `<base>`. The server's TOTP QR arrives as an SVG string; the console parses it, keeps a viewBox and one path of numbers and path letters, and rebuilds the picture itself, so SVG markup from the network never reaches the page.
- **No third-party code.** No CDN, no package, no font or analytics request; the console is meant to work with no route to the internet (air-gapped load owed: `HUBU-*`).
- **Cookie and CSRF.** Session cookie `__Host-` prefixed over TLS, HttpOnly, SameSite=Strict; `X-CSRF-Token` on every state-changing call; the token is kept in memory only. Nothing secret is stored in `localStorage`; the stored items per browser are the step-up key (below) and display preferences.
- **Step-up key.** Dangerous actions need a signature from a key that never leaves the browser: WebCrypto ECDSA P-256, `extractable: false`, held as a `CryptoKey` in IndexedDB, registered with a proof of possession bound to the username and a fresh authenticator code. Honest limits: it protects against a stolen session cookie or a CSRF request (the thief has no key); it does NOT protect against script running on the console's own origin (XSS, which the CSP and the DOM rules above exist to prevent) or against someone using the unlocked browser. Clearing site data loses the key, which is a recovery path (register a new one with a TOTP code), not an incident. WebCrypto needs a secure context: https or `localhost`; over plain http the console says so.
- **Invite links** come from the hub's configured external URL, never from the browser's address bar, and are shown once in the dialog that created them.
- **Not covered:** a compromised administrator workstation, a malicious browser extension, side channels in the WebCrypto implementation.


## Hub sealing key and changed-key policy (ADR-126, 2026-10-13)

- **The key.** Each device has one software P-256 sealing key for hub chat content, separate from its identity key. It is bound to the device by a signature of the identity key over the device id and the public key (`HubAuth.sealingKeyBindingBytes`); the hub stores public material only, and a sender accepts a colleague's key only after verifying that binding against the identity key the organisation certified for that colleague.
- **At rest.** Android: the PKCS#8 bytes are wrapped by an AES-GCM key held in the Android Keystore (not exportable) and kept in app-private preferences that the backup and data-extraction rules exclude. Desktop: the same bytes under the identity key vault (DPAPI on Windows; Secret Service, then an owner-only key file, on Linux) at `<stateDir>/hub/sealing.key`, written atomically. The key is never backed up and never logged (only a 16 hex digit public fingerprint is).
- **Publication.** The key is stored before it is published; a key that cannot be stored is never published. A key the hub remembers as retired (409) is replaced by a new one; unenrol deletes the key at the hub and locally; a confirmed revocation wipes it locally.
- **A changed key is never trusted silently.** The first key seen for a colleague is pinned (SHA-256 of the SPKI). A different verified key for the same device id stops all hub sending to that colleague, sealed or readable, even when "Messages through the hub" is on, until the user taps Continue in the chat. The pin and the pending change are persisted and keep holding while the directory cannot be read.
- **No silent downgrade.** A colleague without a published key receives a readable hub message only when the user turned the switch on; otherwise the message waits and the chat says why.
- **Incoming.** A sealed message is opened only when the sender's signature verifies against the sender's certified identity key; otherwise it is dropped, counted ("Messages not opened") and never stored or shown. A sender that cannot be looked up right now is retried, not dropped.
- **Not covered.** Group messages travel readable through the hub (opt-in) and the UI says so; there is no key-transparency log; the sealing code comparison is by reading the short codes aloud (ADR-126 "Consequences").


## Hub review round: deployment and operations rules (ADR-127, 2026-10-13)

Facts an operator must know. All of it is unit/e2e tested; none of it is device-verified (`HUBR-01`..`HUBR-08`).

- **Back up `data.key` apart from the database.** TOTP seeds in the database are AES-GCM sealed (`enc1:`) under `<data>/data.key`. A copy of the database alone reveals nothing usable; the key without the database is useless; both together are the secrets. Losing `data.key` means every administrator needs `admin-recovery`. The database rows themselves (mailbox payloads, directory) are NOT encrypted at rest: whole-database encryption is an open owner decision (ADR-127 P-4). File permissions are owner-only (POSIX modes, or an ACL on Windows) for the database, `data.key`, `server-identity.pk8`, `setup-token.txt`.
- **Behind a reverse proxy** set `FLASH_TRUSTED_PROXIES` to the proxy's address. Without it every device appears to come from the proxy and shares one per-address limit and one relay connection cap; with a wrong list a client could pick its own address through `X-Forwarded-For`. The hub logs a WARN at start when `FLASH_TLS_MODE=proxy` and the list is empty. Only the rightmost untrusted entry of `X-Forwarded-For` is believed. IPv6 clients are limited by their /64.
- **A compromised hub key** (the delegate key on the server): issue a new delegation (higher serial) for a new hub key FIRST, then `keytool revoke --delegation-serial <old>` with the offline root key (pass the list the hub serves today as `--base` so earlier entries are carried over), install it through the console (`revocation.install`, step-up) and on every other hub that serves the same devices. Devices stop trusting the old serial and everything it issued. Rotate `data.key` and the administrators' passwords as well.
- **Root pin.** The hub trusts the root that signs its first delegation unless `FLASH_ROOT_FINGERPRINT` is set; it logs `TRUST ON FIRST USE` when it had to adopt one. Production: set the fingerprint `keytool init-root` printed and `FLASH_REQUIRE_ROOT_PIN=true`. The Docker image sets `FLASH_REQUIRE_ROOT_PIN=true` by default (owner decision 2026-10-13), so a container whose `FLASH_ROOT_FINGERPRINT` is missing refuses the first delegation and enrolment stays closed; a bare `installDist` or `:server:run` start keeps the default `false`; for a local container trial pass `-e FLASH_REQUIRE_ROOT_PIN=false`. The hub also remembers the highest delegation serial it ever accepted and refuses an older certificate, even after a restart.
- **Keytool serials.** `keytool issue-delegation` never reuses a serial: it takes the highest of `delegation-serial.txt` and every `*.cert` beside the root key or at the output path. Keep the serial file with the root key backup; a missing file is warned about, not trusted.
- **Replacing an administrator's step-up signer** (lost browser key or phone): sign in, then enter one of the administrator's recovery codes (not an authenticator code) when registering the new key. Generating new recovery codes itself needs a step-up confirmation once a signer exists.
- **Setup.** `GET /admin/api/v1/setup/status` reveals only whether setup is open. `setup/begin` needs the setup token (`<data>/setup-token.txt`) and shares its lockout; at most 16 setups can be pending.
- **Public information.** `GET /api/v1/revocations` is public (rate limited per address) so a revoked device can confirm its own revocation; it lists revoked device ids. The owner decided on 2026-10-13 to leave it public (ADR-127 addendum; hashed ids are FO-13), so do not publish the hub address where a list of revoked device ids is sensitive.
- **Docker.** `.dockerignore` keeps keys, `keystore.properties`, `data.key`, setup tokens and tool-state directories out of the build context (checked by `DockerIgnoreTest`); `server/docker-compose.example.yml` binds the hub to loopback behind a proxy, read-only root, no capabilities. Pin the base image by digest for releases (the Dockerfile header says how).
- **Logs.** The log never contains setup tokens, TOTP seeds, passwords, session or CSRF tokens or recovery codes (`LogHygieneTest`). Level INFO by default; `logback.xml` quiets Netty, Ktor, Jetty and SQLite.
- **Audit.** New audit rows use a length-prefixed hash (`flash-audit-chain-v2`); `GET audit/verify` still verifies the older rows.


## Hub: hashed revocations, sealed mailbox, approver phone; desktop chat key (ADR-129..132, 2026-10-14)

- **Revoked ids.** The public revocation list (v3) holds `SHA-256(audience | deviceId)` per revoked device, not the ids. It stops casual reading; anyone holding a candidate id can still test it, so do not treat the list as secret.
- **Mailbox at rest.** Payloads of queued messages are sealed with `data.key` (AES-256-GCM, AAD binds origin, target and message id). A copied database without `data.key` shows no payload. Metadata is still readable. Losing `data.key` loses the queue: back it up apart from the database.
- **Approver phone.** With a phone bound, a stolen browser key plus a stolen session can no longer install a delegation, create or reset an administrator, or replace the signer: the phone must sign the same challenge and the person must compare six digits. If the phone is revoked the hub **refuses** (fail closed) until the account's recovery code removes the phone. Binding the first phone needs a fresh authenticator code, so a session cookie alone cannot name the attacker's phone. Residual risk: a person talked into approving a request they did not start.
- **Desktop chat key.** The chat database passphrase file is wrapped with Windows DPAPI (same vault as the hub sealing key). It protects a copied profile, another Windows user and backups; it does not protect against malware running as the same user. A failed unprotect never overwrites the file.

## Organisation Tier (ADR-134)

Flash establishes a three-tier trust model for peer communication:
1. **Stranger (Tier 1):** Discovered via mDNS/NSD, Wi-Fi Direct, or transport beacon, but neither paired nor attested by an organisation snapshot. All application payload processing is blocked (`isTrustedPeer == false`).
2. **Colleague / Organisation (Tier 2):** Attested by a signed `OrgMemberStatement` chained to an enrolled root certificate, within a valid time-bounded lease (`now <= lastSuccessfulSync + offlineGraceDays`), whose live TLS leaf certificate public key strictly matches the statement SPKI fingerprint (`sha256(statement.subjectPublicKey) == liveTlsLeafSpkiSha256`).
   - Capabilities granted: 1:1 chat messages, deliveries, reactions (`mayReact`), read receipts, typing status, voice/video incoming calls/ringing (`mayRing` — auto-answer strictly forbidden).
   - Capabilities denied: Push-to-talk audio (`mayPushToTalk` requires Tier 3 Paired), group creation/joining (`mayCreateGroupWith`, `mayAddGroupMember`), group administration (`mayAdministerGroup`), vouching (`mayVouch`), and swarm serving (`mayServeSwarm`).
3. **Paired (Tier 3):** Explicitly authenticated via out-of-band numeric SAS comparison (Pairing v2). All capabilities enabled.

### Rule 3.2 TOFU Pin Replacement
When a connection is received from a peer claiming to be an enrolled colleague:
- If a stored pin exists and matches the statement fingerprint, binding succeeds.
- If a stored pin exists from a prior TOFU (Trust-On-First-Use) discovery and differs from the authoritative statement fingerprint:
  - The resolver replaces the TOFU pin in the `trustStore` with the statement fingerprint, logging `org.pin.replaced`.
  - The live session that presented the mismatch fails closed (`bindingOk = false`). The subsequent handshake with the legitimate colleague presenting the correct key succeeds.
  - A stored pin whose source is `PAIRED` or `VOUCHED` is **never** replaced by an organisation statement.

### Clock Skew and Lease Expiration
- Device clock is continuously validated against the snapshot sync timestamp. If `now < lastSyncSuccessMs - 5 min`, clock rollback is flagged (`OrgLease.Expired(reason = CLOCK)`).
- If `now > lastSyncSuccessMs + offlineGraceDays`, the lease expires (`OrgLease.Expired(reason = TIME)`).
- In both expired states, `resolve(deviceId)` returns `null`, immediate offline colleague chat fails closed, and UI renders honest reconnect notices matching Plan B Section 9 strings.

## Threat rows — Announcements (Plan A3, ADR-138, 2026-10-15)

| Threat | Attack Scenario | Mitigation (built) | Residual Risk |
|---|---|---|---|
| **Eavesdropping by hub operator or database extraction** | Hub administrator or attacker with disk access reads announcement content. | Plaintext on hub by design (ADR-138). No claim of encryption anywhere in code, strings, or docs. Console composer and app show explicit honesty notice: `Announcements are stored as plain text on your company's server. Administrators can read them.` | Anyone with read access to `flash-hub.db` or server memory can read announcements. Not end-to-end encrypted. |
| **Impersonation of poster** | Malicious device claims to post on behalf of an executive, department head, or other colleague. | Server strictly derives poster device ID, department, and display name from the authenticated bearer token (`HubApiGate`), not request body fields. Any client-supplied poster fields in JSON are ignored. | Compromised device identity private key allows posting as that device until revoked. |
| **Department head scope spoofing** | Department head attempts to broadcast company-wide (`scope=org`) or to another department. | Server validates caller's role and department. Non-org admins posting with `scope=org` or `departmentId != caller.departmentId` are rejected with `403 ERR_FORBIDDEN` (`org_ann_not_allowed`). | None; role and department membership are enforced authoritatively by the server. |
| **Hidden department announcement leakage** | Outsider in Department A attempts to discover announcements of hidden Department B. | Search (`AnnouncementStore.search`) and changes feed (`AnnouncementStore.getChangesFeed`) apply SQL predicate: `scope = 'org' OR (scope = 'department' AND department_id = ?)`. Outsiders receive zero results for other departments' announcements. | None; filtered authoritatively at SQL query execution. |
| **Notification leakage via OS or push** | Lock-screen notification or push preview reveals sensitive body text. | Server and client push payloads omit announcement body entirely; notifications contain only the title. | Title text may still appear on device lock screens if the user enabled lock screen notifications. |
| **XSS / HTML injection in console or app** | Attacker embeds `<script>` or HTML tags in announcement title or body. | `AnnouncementText.clean` normalizes Unicode, strips bidi overrides (`\u202E`, etc.), zero-width chars, and control chars. Admin console builds DOM strictly via `textContent` and `createElement`, never `innerHTML`. | None; raw HTML/tags are treated as pure literal text. |


## Threat rows — Sealed files through the hub (ADR-215, P1 server and P2 client transport built 2026-10-20)

The hub stores **ciphertext only** and never receives a file key. The first rows describe what the server enforces (P1);
the rows marked *client* describe the P2 transport (`HubFileSealing`, `HubFileTransfers`). Nothing calls the client yet
(P3 wires it into chat), nothing is deployed and nothing is device-verified.
*Update 2026-10-20 (P3):* chat now calls the client for 1:1 files; the rows marked *P3* cover the ticket message. Still
nothing is deployed or device-verified.

| Threat | Attack Scenario | Mitigation (built) | Residual Risk |
|---|---|---|---|
| **Hub operator or database extraction reads a file** | The operator, or anyone who copies `data/flash-hub.db` and `data/files/`, tries to read a transferred file. | The body is client-sealed (AES-256-GCM, ADR-215 D1/D2) before it leaves the sender; the hub stores and returns opaque bytes and one whole-blob SHA-256. No key, no name, no plaintext-derived field is ever sent to the hub. | The hub learns size, timing, sender and recipient ids. Metadata is deliberately not hidden. |
| **Crafted `fileId` used as a path** | A sender posts `fileId` values such as `../data.key` or `..%2f..%2fflash-hub.db` to read or overwrite another file. | `fileId` must be exactly 32 lowercase hex characters (`FileStore.isFileId`) before any filesystem call; the storage path is `files/<fileId>/<index>.chunk` where `<index>` is an integer range-checked against `chunkCount`. No other request value reaches a path. | None known. |
| **A non-recipient downloads the file** | An enrolled device that is not on the recipient list calls `GET /api/v1/files/{id}/chunks/{i}`. | The recipient set is stored at create time and checked on every status/chunk read (`FileStore.access`); a group file is **also** re-checked against the live group roster, so a removed member loses access and a new member never gains it. | A recipient can always forward the key (unavoidable for any E2E file). |
| **Replayed or conflicting chunk overwrites stored bytes** | A device replays a `PUT` with different content for an index already stored, or retries the same chunk. | The per-index SHA-256 is stored with the row: an identical retry answers `204` and changes no counter, a different body answers `409 ERR_CONFLICT` and never overwrites. `create` is idempotent per `fileId` only when every metadata field matches, otherwise `409`. | None known. |
| **Storage exhaustion** | One device (or the whole organisation) fills the hub's disk with uploads. | `maxFileBytes`, `deviceStoredBytes`, `globalStoredBytes` and `maxFilesPerDevice` are checked **inside** the same `BEGIN IMMEDIATE` transaction that inserts the row, so two racing senders cannot jointly overshoot; an unfinished upload counts against the cap from `create`. The sweeper deletes abandoned uploads after 24 h and ready files after `fileRetentionDays`. | An organisation insider can always fill its own allowance. The operator's disk is protected only up to `globalStoredBytes`. |
| **A cancelled or expired file lingers on disk** | After a cancel, an expiry or a crash, the ciphertext stays readable on the server disk. | `DELETE` removes the rows and then the directory; the sweeper deletes expired/abandoned files and their rows; the startup consistency pass removes orphan directories and drops chunk rows whose bytes vanished. | A crash between the database commit and the file delete is repaired by the next pass, not instantly. |
| **Secrets in logs or audit** | Content, keys, file names or whole ids appear in the audit chain or the log. | Audit actions (`file.create`, `file.chunk`, `file.complete`, `file.read`, `file.cancel`, `file.sweep`) carry the first 8 characters of the id, the chunk index and byte counts only. `nameHint` is stored but never returned, never shown and never audited. | An operator can read the per-file hint it typed itself. |
| **A restore without `files/` pretends a file is intact** | The database is restored from a backup that did not include `data/files`. | A chunk row whose file is missing answers `503` (never an empty body), and the sweeper removes the row after retention; `complete` refuses to mark such a file ready. | The recipient must ask the sender to send again. |
| **A hostile or broken hub serves other bytes** *(client)* | The hub (or anything between it and the device) returns a chunk from another file, another index, a truncated or a flipped chunk, or claims different sizes. | Every chunk is AES-256-GCM with the chunk index, file id, chunk count and plaintext length in the AAD and the index in the nonce: a moved, swapped, truncated or altered chunk does not open. The download first checks the hub's status against the sender's ticket (id, ciphertext hash, sizes, count, sender) and fetches nothing on a mismatch; a chunk body longer than expected is never read past `expected + 1` bytes; the assembled file is re-sealed and its hash compared with the sender's before it is handed over. | A hub can refuse service (withhold or delete a file); that is visible as a failed download, not as wrong content. |
| **A file key stolen from the device** *(client)* | Malware or a backup extraction reads the upload record under `<root>/up/<fileId>.state`, which holds the file key until the upload is released. | The record lives in app-private storage next to the plaintext it protects (the key gives nothing the source file does not already give); P3 calls `releaseUpload` once the message is stored, which deletes the record. No key is logged, `HubFileKey.toString()` is redacted, probes carry 8-character ids. | A device whose private storage is read loses its files anyway. Android Auto Backup / desktop backup rules for the record folder are P3 work. |
| **Nonce reuse by a resumed upload** *(client)* | A resumed upload seals a *different* plaintext under the key and index of a chunk that already left, which with GCM leaks the XOR of the two plaintexts and the authentication key. | The key and the ciphertext hash are saved before the first byte leaves; a resumed run re-hashes its source and, when anything changed, withdraws the upload (`DELETE`) and ends with `SourceChanged` instead of sealing new bytes. A record whose key does not decode is withdrawn the same way. Sizes and layout in a record must agree with each other or the record is refused. | A source that changes and changes back between two reads of the same chunk inside one run is not detected; the recipient's whole-file check then fails. |
| **A state record edited on disk** *(client)* | Something writes the state file to point at another hub, another file id or an inconsistent layout. | The record carries a SHA-256 check line, every field is shape-checked (id 32 lowercase hex, sizes in range, layout consistent, bitmap without stray bits), and a record for another hub is never resumed (`NotThisHub`). A record that fails any check starts the transfer over instead of trusting it. | The check line is an integrity check against torn writes, not a MAC: a process that can write app-private storage can forge it (it could also replace the source file). |
| **The file key travels readable** *(P3)* | A device with readable hub content switched on (`contentViaHub`) sends the ticket as a readable hub frame, so the hub operator reads the key and then the file. | `HubChatBridge.sendHubFile` seals or sends nothing (no readable fallback), and an inbound `HUB_FILE` that did not arrive in a sealed envelope is rejected even when readable content is allowed (HUBFILE-U16/U18; mutation-checked). A peer without a published sealing key gets a Failed row with `HUB_FILE_NEEDS_SEALING` before any byte is uploaded. The ticket never goes over the LAN either (D17). | None known for the key; the hub still sees the ticket's size and timing as with any sealed message. |
| **A forged or replayed ticket** *(P3)* | A colleague sends a ticket naming another person as the author, or reuses a known file id with another key or sender to swap the file under an existing message. | The ticket's author must equal the sealed envelope's sender (mutation-checked). A file id already stored from another sender or with another key is refused and logged with 8-character ids; a byte-identical replay is a duplicate that only earns its receipt. Every field is bounded by `HubFileFrameCodec` (chunk size, count matching the layout, a safe name, no group id). | A colleague who is a real recipient can always send a file it chose; it cannot pass it off as someone else's. |
| **A file name that escapes the received folder** *(P3)* | A ticket names the file `../../evil` or an absolute path. | The name is sanitised when the sender claims the send and again when the receiver places the file; the file goes to `<received>/<transferId>/<name>` with the transfer id built from the 32-hex file id (HUBFILE-U34). | None known. |
| **A file from a stranger downloads by itself** *(P3)* | An organisation colleague the person never paired with sends a large or unwanted file, and the per-type auto-download setting fetches it. | Automatic download needs a paired sender **and** the per-type setting (AGENTS.md section 19, D18 refined); a file from an unpaired colleague waits with Accept and Decline. | A paired peer can still fill the auto-download allowance the person chose. |
| **File keys at rest on the device** *(P3)* | A backup or a copy of app storage reads the keys of received and sent hub files. | The keys are in the `hub_file` table of the chat database, which carries the same protection as the messages themselves; the engine's upload record (which holds a key until the upload is released) is under `noBackupFilesDir/hub-files` on Android (never in Auto Backup) and `<stateDir>/hub-files` on desktop, and is released once the ticket is stored. | Someone who can read the chat database can read the files anyway. The desktop state folder has no backup exclusion because the app runs no backup. |
